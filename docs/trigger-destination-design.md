# Queue and schedule triggers with output destinations

## Scope and implementation boundaries

This is the design specification for [#337](https://github.com/DeandreT/weft/issues/337), not a statement of implemented or qualified behavior. It covers Service Bus queue/subscription inputs, cron-driven Blob/SFTP inputs, Blob/SFTP/HTTPS/Service Bus topic outputs, per-target configuration, Operations/API/CLI, offline templates and emulator acceptance. It introduces no new mapping engine or catalog-writing runtime path. Implementation must not create CI pipelines or provision live Azure resources without separate authorization.

Read alongside [archive and deletion](archive-deletion-design.md), [organization switching](organization-switching-design.md), [machine authorization](machine-authorization.md), [mapping endpoints](mapping-endpoint.md) and [release operations](release-operations.md). Archiving does not stop an already deployed runtime. Explicit target disable, retirement, grant revocation, approval/environment revocation and payload retirement still fence execution/delivery. Runtime admission follows target/release lineage, not the authoring archive epoch.

All triggers and destinations remain disabled until their required settings, authority and connector capabilities are explicitly configured and admitted. Missing settings are refused, not filled from inferred production defaults.

Required extensions: claims do not return/persist an active-release pin; a retry resolves the current release. `machine_invocation_provenance` verifies an activated release's identity, not that it is still the current pointer. The service checks the pointer before finish, leaving a check-to-commit race for asynchronous output. `LocalReleaseInvocation` has no expected-release argument. Existing 24-hour results alone cannot support a durable delivery backlog.

## Runtime and authority boundary

- Add a dormant trigger/delivery worker in the existing .NET hosting/jobs structure; compose the same compiled runtime and release services as `MappingEndpointResources`. Do not host mapping execution in a scheduler adapter or notification worker.
- Operator-private configuration registers immutable, project-scoped connector IDs and versions: endpoint identity, allowed prefix/path, authentication profile, capabilities and destination limits. API users select IDs and bounded policies, not arbitrary network endpoints or secret paths.
- Managed identity supplies Azure data-plane credentials and the validated machine caller; protected private files supply local/emulator connection strings, SFTP keys and webhook credentials. Database rows contain references and non-secret configuration only, never tokens, passwords, private keys, SAS URLs or credential hashes.
- Freeze a non-secret connector configuration fingerprint/version on each work/delivery. Rotation may change credentials for the same identity, never silently redirect retained deliveries. Missing old configuration blocks them.
- Reuse release reader/writer credentials for Operations reads and administrator-only configuration functions. Introduce a separate CONNECT-only `weft_trigger_worker` with narrowly scoped source, work and delivery functions, no table access, grant administration, catalog writes, release mutation or AI quota access.
- Extract shared owner-only ledger internals behind the existing invocation wrappers and new trigger wrappers. Preserve endpoint login privileges; do not give the new worker arbitrary `FinishAsync` authority or grant the endpoint input-receipt access. Guards admit the new role only through validated work/key/claim relationships, not a caller-set trusted flag.
- Admission, execution finish and delivery admission recheck current target, grant and publisher/build authority. Archive is not a stop switch; a retired target is permanently unavailable. Keep Operations available for authorized inspection/containment of archived deployments.

## Minimal persistence

All identities are organization-scoped with full target foreign keys; use existing RLS, owner-defined functions, exact schema admission and append-only event guards. Names below are new tables, not existing ones. JSON policy columns have closed schemas, no arbitrary adapter options.

| Table | Essential fields and constraints |
| --- | --- |
| `trigger_configurations` | Immutable `(org, trigger_id, version)`; target, kind, source binding/version, validated caller/application identity, parameters/media profile, named-input references, destination/output selections, schedule and bounds. One source-binding identity survives edits. |
| `trigger_controls` + `trigger_operations` | Current config version, enabled/retired, monotonically increasing control generation; operation UUID, actor, original expected version, request digest and outcome. Retirement is one-way; no edit implicitly resumes work. |
| `trigger_runs` | Run ID, trigger/config version, scheduled UTC instant or queue parent, pin, state, lease token/generation/expiry, scan progress, counts. Unique schedule occurrence `(org, trigger_id, schedule_epoch, scheduled_utc)` and queue parent `(org,target,caller,source_binding,message_id)`; queue parents retain complete child-manifest digest/count and settlement state. Separate scan completion from child delivery completion. |
| `trigger_work` | One logical order: work ID, trigger/run, immutable source identity/raw-source digest, original message/item identity, request UUID, caller/application, request digest, complete release pin, frozen output routing, current phase and fenced execution claim. Unique `(org,target,caller,source_binding,source_identity,order_key)` independent of config/run version. |
| `trigger_receipts` | Append-only input/output receipt identities, digest, size, media, output name, provenance and timestamps. Owner is exactly one work item or queue-parent run (its input manifest). Input and output are separate receipts; input per owner and output per work/name are unique. Source identity details are private, not Operations text. |
| `trigger_payloads` | Private bounded exact bytes linked to receipts, independently retained from audit and catalog artifacts. Reuse exact-byte/digest verification concepts, not `NativeArtifact`/`DerivedArtifact` IDs: those are not trigger payload classes. |
| `trigger_deliveries` + `trigger_events` | Delivery UUID, output receipt, frozen destination/version, deterministic remote key, phase, claim/generation/expiry, bounded attempt count/next time; immutable attempt/observation/failure/settlement events. Unique `(work,output_name,destination_binding_version)`; immutable request bytes and remote identity on every retry. |

- Release pin = release/qualification/build/revision IDs, publisher, build-intent/artifact digests and runtime image, plus the observed target generation and exact active invocation grant ID. Store it once at work admission. Target generation changes invalidate outstanding admission tokens, even after disable/enable. Revoking the pinned grant permanently fences this work's automatic execution/delivery, even if a new grant later admits the same principal. Existing HTTP-ledger replay behavior stays unchanged; durable trigger backlogs do not silently inherit its ability to resume after revoke/regrant.
- Payload retention and pending-storage caps must be explicitly configured before enabling. Never silently expire bytes needed by queued or uncertain deliveries; pressure blocks new admission and is visible. Explicit retirement/purge records unavailability and cannot cause re-execution to regenerate bytes.
- Keep permanent compact source/idempotency tombstones, even after payload expiry. Missing output bytes means `payloadUnavailable`, not permission to rerun a completed order.

```text

ITriggerWorkStore.ClaimRunAsync / RecordDiscoveryPageAsync / FinishScanAsync

ITriggerDeliveryStore.ClaimAsync / RecordObservationAsync / RecoverAsync

```

- Add `MachineInvocationService.InvokeTriggeredAsync(workContext, caller, request, token)` sharing `InvokeAsync`'s core. Add `LocalReleaseInvocation.ExecutePinnedAsync(..., expectedReleaseId, ...)` via the same implementation, refusing a different pointer before selecting a build. Keep the existing HTTP contract unchanged.
- `ClaimPinnedAsync` atomically binds/checks the existing ledger key and the stored pin; it returns the stored publisher/claim. `FinishAndEnqueueAsync` is one database transaction, not calls to `FinishAsync` followed by a separate outbox insert.
- New ports reject incorrect config, caller, key, request digest, release, claim or output membership. SQL derives destinations from the frozen configuration; the worker cannot substitute an endpoint or claim arbitrary delivery success.

## Transaction and race protocol

1. Validate a bounded source envelope and obtain current validated machine identity. Look up its stable source identity first: a redelivery reuses stored inputs/parameters/routes/pin, not the current config. New work resolves explicit named inputs/parameters and verifies bytes. No source-controlled target, caller, executable, URL or destination selection.
2. Admission transaction: lock current authority scope, target, active grant, then control/source identity. Re-read clocks after waits. Check enabled/not retired, admitted config, capacity and current release. Insert original input receipt/bytes, immutable pin, work and event together, or recover the existing matching work after concurrent insertion. Changed raw source content/application under the same identity conflicts without changing the winner; changed current configuration does not change its request digest.
3. Claim transaction: serialize short admissions per target, enforce aggregate target concurrency across replicas, then lock ledger and work in the common order. Verify control generation, exact active release and grant again. Start the existing 120-second ledger claim and bounded worker lease. No database lock remains held during I/O/execution.
4. Execute through the shared pinned path as the stored publisher. Maintain the endpoint's 85-second work / 90-second overall envelope, including settlement, below the ledger lease; do not renew that lease indefinitely. An unfinished attempt may be reclaimed only under the same pin, request and input bytes.
5. Finish transaction: recheck live claim/deadline, authority, target generation/pointer, exact provenance and output grammar. Share the ledger finish logic; atomically commit final ledger outcome, exact response/output receipts, required delivery rows and metadata events. A nonfinal infrastructure outcome releases the attempt; revoked/superseded work retains no deliverable output. Never commit `completed` without all outbox rows.
6. If commit acknowledgement is lost, recover by the original work/key/digest. Do not execute again merely because local code missed a response. Existing final ledger success must have its matching output/outbox receipt; a missing receipt is integrity failure, not a repair-by-remap opportunity.
7. Delivery claim transaction: check live control/target generation, current active release equals pin, grant, publisher/approval and destination admission; lock one pending delivery, establish immutable attempt identity and deadline. Load only its verified output bytes. Send outside the transaction.
8. Persist the adapter's bounded observation against that exact attempt. `accepted` requires defined provider evidence; absence of acknowledgement is `unknown`. Retain late/stale observations for reconciliation but never let an expired claim overwrite a newer state or authorize another send. Every execution/delivery admission and finalization must check the original pinned grant ID is still active, not merely find any current grant for the same principal. New grants never revive fenced backlog. Explicit administrator resolution may create linked new work after reviewing prior outcomes and duplicate risk, but may not clear an uncertain result or automatically repeat its send.
9. Disable/retire/revoke prevents new claims and cancels admitted work best-effort. A network request already admitted may have been accepted remotely; retain that fact/uncertainty rather than labeling it not sent. There is no transaction spanning PostgreSQL and remote systems.
10. Standardize shared SQL lock order before adding wrappers: authority scope (when needed), target, grant, ledger, trigger/work, delivery. Existing claim locks target before ledger, but finish locks ledger before target. Normalize this shared core and exercise mixed old/new callers; do not wrap those opposite orders under new locks. When integrated with lifecycle operations, acquire their common organization gate first and follow their full scope ordering; this target/grant/ledger order applies within that shared boundary, not instead of it.

After activation/rollback, pending work with an old pin becomes `releaseSuperseded`; never silently run or send it under a new release. Explicit operator resolution creates a linked new work identity after reviewing duplicate risk. Already recorded remote acceptance remains history. A disable/enable cycle does not revive suspended deliveries automatically.

## Service Bus input and order isolation

- Use PeekLock, `AutoCompleteMessages=false`, explicitly bounded prefetch and target concurrency within the existing 1–4 runtime limit. Bounded message size, work budget and maximum lock-renewal duration must be configured and below the overall settlement envelope.
- Idempotency scope is target + validated principal + immutable source binding (namespace, queue or topic/subscription) + exact case-sensitive `MessageId`. Store a generated UUID once for the existing ledger; never parse/truncate the broker string into a UUID. Config edits and redelivery do not create a fresh key. Sequence number/lock token/delivery count are observations, not the identity.
- One admitted work unit is one complete logical order, including its named inputs. Require an explicitly selected single-order envelope or supported batch envelope. For a batch, materialize its complete bounded child manifest first; extend the identity by explicit stable order key, and retain parent settlement state. Never split arbitrary EDI/text heuristically.
- Every child gets its own ledger boundary and outbox. A failure at start/middle/end does not prevent other orders from running; successful children remain successful on corrected retry. Corrections require a new explicit source version/linked work identity only for failed children, not reuse of an ID with different bytes.
- Renew broker locks only while this receiver owns the original message and before the configured ceiling; stop renewing after cancel/lock loss. Broker lock loss cannot authorize a second ledger claim. A new receiver resumes/replays the original work and settles with its own lock token.
- Settlement contract: complete the message at durable output/outbox handoff, only after all child mapping outcomes and successful-child outboxes are durable. Dead-letter terminal mapping/input failures with fixed category and private braid work ID; partial-batch dead letter reports partial outcome, not loss of successful children. Delivery acceptance happens independently after this handoff, and later delivery failures are tracked in braid's outbox, not the broker DLQ.
- Fixed dead-letter reasons: `invalidEnvelope`, `unsupportedFormat`, `idempotencyConflict`, `invalidInput`, `invalidParameter`, `executionFailed`, `resourceLimit`, `integrityFailure`, `releaseSuperseded`, `authorizationRevoked`, `attemptsExhausted`. Never put payloads, URLs, parameters or exception/provider text in broker diagnostics.
- Busy/infrastructure/no-release conditions are bounded deferred/abandoned retries of the same identity. Configure the broker's delivery/TTL policy consistently with ledger attempts; exhausted work dead-letters, never loops. Shared authentication/infrastructure failure pauses only the affected connector; malformed orders do not become a service-wide admission gate.
- Broker-expired or broker-MaxDeliveryCount dead letters retain their actual broker category; a read-only DLQ observer may expose them in Operations but must not invent a mapping outcome or automatically replay them.
- Failed or uncertain Complete/DeadLetter is recorded as settlement unknown; the next delivery consults durable work. No invented success, new message ID or automatic DLQ resubmission. Destination failure after completion appears as an Operations delivery dead letter, not a falsely claimed native Service Bus DLQ transfer.

## Cron, source versions and checkpoints

- Require an explicit five-field cron grammar/version, IANA timezone, effective start instant, DST gap/fold behavior and timezone-data version. UTC is a selectable value, not an unstated default. Reject ambiguous day-of-month plus day-of-week expressions unless their combination rule is explicit.
- Supported explicit DST selections: nonexistent local time `skip`; repeated time `first`, `second` or `both`. Persist resolved UTC occurrence and offset. The same occurrence is unique across replicas/restarts; a timezone-rules change is a reviewed schedule revision, not retroactive rescheduling.
- Require `skipIfRunning` and a catch-up selection: `none` records missed occurrences; `bounded` requires lookback, occurrence limit and chronological ordering. Lease expiry permits recovery of the same run, not another overlapping run. A skipped overlap never advances a source checkpoint. No unbounded catch-up on startup.
- A run snapshots an observation cutoff and scans bounded pages/files/bytes/wall time. Persist each discovered source-version work item and the next page cursor in the same transaction; finish a scan only after its admitted scope is fully enumerated. Cursor means discovered, not mapped/delivered.
- Listing uses repeated bounded full-prefix passes with persisted continuation and source-version deduplication. A timestamp high-water mark alone is unsafe for late/backdated files and inconsistent listings. Interrupted/over-limit scans stay incomplete; continue the same pass rather than claiming no inputs.
- Blob identity = source binding + exact blob name + version ID, or ETag under a conditional read when versioning is unavailable. A changed/missing listed version records `sourceChanged`/`sourceMissing`; never process replacement bytes as the old version. A later pass admits a newly observed version separately.
- SFTP requires a producer readiness contract, preferably atomic publication of a manifest containing stable file/version/order ID, length and digest, then immutable content. Size/mtime stability alone cannot establish an exact snapshot. Pin host key, reject symlinks/traversal and enforce the registered root. Refuse enabling without a verifiable readiness/version strategy.
- Retain failed discoveries/work independently of the cursor so good files continue. Never advance past an undiscovered page or forget a failed order. Do not delete, rename or acknowledge source files as a side effect; such behavior needs separately approved policy.

## Output adapters and honest retry semantics

All required outputs are explicit by qualified output name/media. Delivery success is per output/destination; overall order is delivered only when every required route has an accepted receipt. Fan-out is not atomic across destinations. Never rerun a mapping to retry delivery.

| Destination | Required minimal contract |
| --- | --- |
| Blob | Immutable deterministic key containing delivery ID; create-only conditional write. Existing object succeeds only after matching receipt identity, length, metadata and verified content digest. Mismatch is conflict; no unconditional overwrite. Capture ETag/version and acceptance time privately. |
| SFTP | Delivery-specific temporary file, verified upload, then atomic **no-replace** publish within the same registered root. Require supported server semantics or cooperative exclusive-publish contract. Existing final file must be verifiably the same delivery/content; unsupported atomicity is refused, not simulated with stat-then-rename. |
| HTTPS | Exact frozen bytes, output media, stable `Idempotency-Key`/delivery ID and digest. An ambiguous outcome requires manual resolution and is never automatically retried. Pin safe connection policy from notifications, not its metadata message shape. Configured success codes mean remote acceptance only; 202 is not downstream completion. |
| Service Bus topic | Stable delivery ID as `MessageId`, fixed topic, frozen properties/body, bounded send. Broker acknowledgement means accepted by the broker, not processed by subscribers. An ambiguous send outcome requires manual resolution and is never automatically retried. |

- File outputs are explicitly configured and create-only with deterministic keys. Overwrite and append are not supported; there is no split-name guessing or newest-file replacement. Unconfigured routes are refused.
- Separate `notAttempted`, `accepted`, `retryableKnownNotAccepted`, `unknown`, `permanentFailure`, `fenced`, `payloadUnavailable`. A timeout/cancellation/reset after request dispatch is not known failure. HTTPS 5xx is not proof the receiver made no change.
- Disable hidden SDK retries for mutations unless the adapter's exact remote key/content conditions make them safe. Bounded automated retry is allowed only for proven non-acceptance or where Blob/SFTP create-only key/content conditions make a repeat safe. Ambiguous HTTPS and topic outcomes are held `unknown` for manual resolution; never show guessed success.
- An expired send lease with no durable observation becomes `unknown`, never automatically pending. Recovery may inspect remote evidence, but another send needs those create-only conditions or an explicit reviewed resolution. Missing acknowledgement is not a fresh-send permit.
- An operator retry/resolution is version-conditional and idempotent, retaining the same delivery ID/bytes for recovery. Mark accepted only with evidence; forcing a potentially duplicate resend needs explicit acknowledgement and audit, not a generic Retry button.

## Operations, APIs, audit and quotas

- Extend existing Operations routes/components (`ReleaseOperationsEndpoints`, `ReleaseOperationsV1`, `operations-api.ts`, `operations-page.component.*`) rather than adding a competing dashboard. Add trigger/run/work/delivery/dead-letter metadata, pins, counts, fixed outcomes and settlement uncertainty.
- Reads: `.../operations/{target}/triggers`, `/runs`, `/deliveries`, `/dead-letters`; configuration/action writes use `.../triggers/{trigger}/actions/{operationId}` and delivery resolution uses its own resource-version `If-Match`. Use bounded existing page/window conventions and closed request DTOs.
- `ITriggerAdministrationStore` follows `RecoverAsync` before current-state mutation, stores admitted failures, checks same actor/body/expected version, and refuses an ID collision. Do not overload release activation bodies or replace their target-version semantics.
- Reads retain current Publisher/Administrator access; trigger/destination edits, enable/disable/retire and replay/resolution require current Administrator. Machine credentials cannot administer. Payload reads are absent from these metadata APIs; any later download requires a separately authorized, audited payload boundary.
- Extend `weft operations` via generated OpenAPI contracts with matching IDs/version requirements. Browser/CLI never auto-retry a mutation after an uncertain reply; retain original operation for explicit recovery. Wrong identity hides/clears retained state using existing session rules.
- Add new source event projections to the existing audit journal in the same transaction, with IDs, actor, category and timestamps only. Update audit kind filters/contracts explicitly if new kinds are chosen. Do not log source filenames, endpoint URLs, payload digests, raw errors or credentials in the general audit.
- Preserve `MachineInvocationRoleGuard`, `ReleaseOperationsRoleGuard`, audit, Automation and AI schema admission as complete contracts. Verify additive objects before exclusions; do not loosen fingerprints or grant inheritance. No catalog/project/mapping metadata writes from the worker.
- No AI turn/provider calls, token-count estimates, quota reservations, quota releases or usage attribution for mapping/delivery work. Operational byte/concurrency/backlog caps are independent settings. Regression tests must prove audit/usage/quota behavior remains unchanged.

## Acceptance requirements

- Pure tests: canonical source identity and digest conflicts, exact media/output routing, cron boundaries/DST folds/gaps/timezone changes, catch-up limits, incomplete scans, connector/path/URL admission, typed error classification and retry eligibility.
- Real PostgreSQL tests: old and new roles, tampered/partial schema rejection, complete audit capture, concurrent duplicate admission/claims, CAS recovery, revoke/disable/retire/activate at each race barrier, original publisher checks, late lease finish, and atomic ledger-output-outbox rollback. Revoke/regrant with the same principal must leave old trigger backlog fenced while preserving the established HTTP-ledger behavior.
- Crash/restart tests at each boundary: input commit, ledger claim, before/after finish commit, before send, remote accept before acknowledgement, observation commit, and broker settlement. Confirm no rerun of completed mapping, no duplicate successful child, no unknown result labeled accepted.
- Source/order tests: valid-failing-valid at start/middle/end, corrected failed-only retry, partial batches, redelivery with changed body/application, equal message IDs on different entities/principals, Blob replacement mid-read, late files, SFTP partial upload/manifest change, and scan interruption after every page.
- Delivery tests: fan-out partial success, output expiry/pressure, corrupt receipts, duplicate keys with equal/different bytes, SFTP no-replace capability absence, HTTPS ambiguous acceptance, topic deduplication-window expiry, post-disable acceptance observations, and no implicit destination redirect on config rotation.
- UI/API/CLI tests: role loss, missing/stale If-Match, operation collision, uncertain mutation recovery, metadata privacy, explicit unknown/partial states, disabled capabilities, and generated OpenAPI parity. Preserve existing audit and quota tests.
- Local acceptance: additive opt-in Compose profile with Service Bus emulator, Azurite, fixed-host-key SFTP and HTTPS receipt fixture, against the existing runtime. Test production policy failures separately from Development-only loopback/secret fixtures; emulators cannot qualify managed identity or cloud RBAC.
- Offline Bicep: extend existing `deploy/azure/modules/mapping-endpoint.bicep`/hosting conventions with opt-in worker and existing resource references, least-privilege receive/send/storage roles and secret-file delivery. Validate/lint/render offline; provision nothing and create no CI pipeline. Live Azure execution and qualification require separate authorization.

## Delivery behavior and required configuration

1. Outputs use create-only deterministic keys; overwrite and append are not supported. Every required output route is explicitly configured; unconfigured routes are refused. Collisions follow the per-destination rules above: matching delivery identity and content succeeds, a mismatch is a conflict.
2. A queue message completes at durable output/outbox handoff. Later delivery failures are tracked as Operations delivery dead letters in braid's outbox, not the broker DLQ.
3. HTTPS receiver and Service Bus topic deliveries whose outcome is ambiguous require manual resolution and are never automatically retried.
4. Schedules require an explicit cron expression and IANA timezone (UTC is selectable, never assumed), plus explicit DST, catch-up and overlap selections. The source readiness/version contract, one-order versus explicit batch envelope, named-input snapshot binding and corrected-order identity are explicit trigger configuration. Missing choices block enablement; there are no inferred shipping/business defaults.
5. Output from a stale release that is still awaiting delivery is held/fenced as `releaseSuperseded`; it is never repinned or resent.
6. Disable/retire stops new admissions but cannot retract an already admitted remote request; its recorded or `unknown` outcome is retained.
7. Operators must explicitly set retry/backoff and lock-renewal ceilings, payload retention and backlog caps before enabling. There are no inferred defaults.
