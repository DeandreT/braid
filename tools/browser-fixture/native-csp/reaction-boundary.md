# Bounded load receipts and promise publication

`Audits.readBraidBoundedLoad({epoch}) → {generation, producer}` extends `readBraidZero` for the mapped HTML fixture only. It certifies settlement of the **original load producer and enrolled CSP dispatch scope**, with an additional rejection rule. It is not a verdict on all script, a page, or a run.

Before document construction the native reservation records the main-thread isolate's publication revision and enables observation for the rest of this dedicated fixture renderer. Any intervening V8 promise-hook notification, Blink message-port submission, frame resource send, or IndexedDB open on that tracker invalidates a later bounded read. The revision saturates rather than wrapping and does not decrease on resolve, return, transfer, failure or disposal. An absent/unsupported tracker refuses. Other worlds on the same isolate may conservatively disqualify an otherwise idle document. The qualification hook composes with the pinned Blink task-attribution tracing hook; it does not install per-context JS hooks, collect page data, cancel work or pump queues. A callback on another isolate is **not** thereby enrolled.

The positive control is a finite static HTML response with no external resources (including the icon), no page callback and no worker. Its load completes on the native `LoadEventFired` path. Its response body is test input, **not a runtime whitelist**. A receipt is time- and producer-scoped, not an assertion that the page is inert. A settled promise with no side effect is deliberately refused: absent proof of the callback's descendants, the implementation cannot admit even that promising-looking case.

In `browser-fence-control.mjs` the zero scenario journals each bounded generation/producer identity **before** replacing or disposing its original. The separate cumulative HMAC prefix commits the run, epoch, contemporaneous native inventory digest and revision. The existing signed fence checkpoint commits that prefix; its outer sequence is still one. This does not authorize a different `prepare` revision, or imply that unobserved generations have acknowledgments. No new successful branch exists in `Browser.verifyBraidDisposal`.

## Why not retire at promise resolution or callback return?

Chromium 157 includes these producer handoffs:

- In V8 `src/builtins/promise-abstract-operations.tq`, `PerformPromiseThenImpl` links a reaction onto a **pending promise**, rather than enqueuing a job. When settled, `TriggerPromiseReactions` turns the stored reactions into jobs. `src/builtins/builtins-async-gen.cc` also has a fulfilled-value `await` path that can enqueue directly. Intercepting JavaScript `.then` or taking a microtask queue snapshot misses real paths.
- `v8/include/v8-promise.h` defines `kResolve` at the **beginning** of resolution, not at completion of dependents. `PromiseReactionJob` can forward to the result promise or resume a generator; `promise-resolve.tq` can enqueue a thenable job. The retained build has `v8_enable_javascript_promise_hooks=false`. The isolate callback is notification, not a transfer ledger.
- Blink `MessagePort::postMessage` serializes and submits to Mojo; `start()` begins receiving and `DispatchMessageEvent` calls into the receiving context. A fulfillment handler can return its final scalar and leave the message queued on an unstarted port. Suppressing delivery to get a zero count would change behavior. Frame resource callbacks also outlive the call to `ResourceLoadObserverForFrame::WillSendRequest`.
- `IDBFactory::OpenInternal` creates an `IDBOpenDBRequest` and defers opening through permission/IPC. The browser's IndexedDB `ConnectionCoordinator` can remain in `kPendingNoConnections`; `OnNoConnections` resumes the same request. `IDBOpenDBRequest::OnOpenDBSuccess` subsequently delivers to Blink. This path needs no JS promise. A per-isolate reaction ledger alone cannot decide that the browser has no such requests.

## Runtime controls and rollout boundary

Use the same private pair, short private `TMPDIR`, loopback-down namespace, and enabled sandbox as the fixture README. Run `timeout 75 node "$FIXTURE/reaction-boundary.mjs"` inside that namespace. It covers the original unresolved promise, a completed `.then` posting to an unstarted port, `await` posting to that port, direct port publication, a settled-only promise, a held image response and a blocked IndexedDB upgrade. The barriers are actual native protocol responses, request arrival, `blocked`, or posted-message delivery; deadlines are failure bounds, never admission criteria. In the database control the old load-only method may return, the stricter method must refuse, and releasing the original connection must still allow the trusted CSP violation to occur.

**Packaged adapter:** this method is not `producerCovered`. Legitimate catalog promise/network activity is an unsupported admission, not something to filter until a test passes. Admitting such contexts needs original-generation credits acquired before registration/publication, transferred to each child (including browser-service operations), and settled only on actual completion, cancellation or recorded loss. The signed prepare/verify session must serialize those transfers against new ingress, including work from other renderers. The veto is a negative filter and the load receipt a bounded positive fact; neither establishes that inventory. Keep the collector disabled.
